## 问题所在

来自 Andrej 的推文：

> "模型会代你做错误假设，然后不假思索地执行。它们不管理自身的困惑，不寻求澄清，不呈现矛盾，不展示权衡，在应该提出异议时也不反驳。"

> "它们真的很喜欢把代码和 API 搞复杂，堆砌抽象概念，不清理死代码……明明 100 行能搞定的事情，非要实现成 1000 行的臃肿架构。"

> "它们有时仍会改动或删除自己理解不足的代码和注释，即使这些内容与任务本身无关。"

## 解决方案

四个原则，集中在一个文件中，直接解决这些问题：

| 原则 | 解决什么问题 |
|-----------|-----------|
| **编码前思考** | 错误假设、隐藏困惑、缺少权衡 |
| **简洁优先** | 过度复杂、臃肿抽象 |
| **精准修改** | 无关编辑、触碰不应碰的代码 |
| **目标驱动执行** | 通过测试优先、可验证的成功标准 |

## 四个原则详解

### 1. 编码前思考

**不要假设。不要隐藏困惑。呈现权衡。**

LLM 经常默默选择一种解释然后执行。这个原则强制明确推理：

- **明确说明假设** — 如果不确定，询问而不是猜测
- **呈现多种解释** — 当存在歧义时，不要默默选择
- **适时提出异议** — 如果存在更简单的方法，说出来
- **困惑时停下来** — 指出不清楚的地方并要求澄清

### 2. 简洁优先

**用最少的代码解决问题。不要过度推测。**

对抗过度工程的倾向：

- 不要添加要求之外的功能
- 不要为一次性代码创建抽象
- 不要添加未要求的"灵活性"或"可配置性"
- 不要为不可能发生的场景做错误处理
- 如果 200 行代码可以写成 50 行，重写它

**检验标准：** 资深工程师会觉得这过于复杂吗？如果是，简化。

### 3. 精准修改

**只碰必须碰的。只清理自己造成的混乱。**

编辑现有代码时：

- 不要"改进"相邻的代码、注释或格式
- 不要重构没坏的东西
- 匹配现有风格，即使你更倾向于不同的写法
- 如果注意到无关的死代码，提一下 —— 不要删除它

当你的改动产生孤儿代码时：

- 删除因你的改动而变得无用的导入/变量/函数
- 不要删除预先存在的死代码，除非被要求

**检验标准：** 每一行修改都应该能直接追溯到用户的请求。

### 4. 目标驱动执行

**定义成功标准。循环验证直到达成。**

将指令式任务转化为可验证的目标：

| 不要这样做... | 转化为... |
|--------------|-----------------|
| "添加验证" | "为无效输入编写测试，然后让它们通过" |
| "修复 bug" | "编写重现 bug 的测试，然后让它通过" |
| "重构 X" | "确保重构前后测试都能通过" |

对于多步骤任务，说明一个简短的计划：

```
1. [步骤] → 验证: [检查]
2. [步骤] → 验证: [检查]
3. [步骤] → 验证: [检查]
```

强有力的成功标准让 LLM 能够独立循环执行。弱标准（"让它工作"）需要不断澄清。

## 核心洞察

来自 Andrej：

> "LLM 非常擅长循环执行直到达成特定目标……不要告诉它该做什么，给它成功标准，然后看着它完成。"

"目标驱动执行"原则正是捕捉了这一点：将指令式指令转化为带有验证循环的声明式目标。

## 如何判断它在起作用

如果你看到以下情况，说明这些指南正在发挥作用：

- **diff 中不必要的改动更少** —— 只有请求的改动出现
- **因过度复杂而导致的重写更少** —— 代码第一次就写得简洁
- **澄清问题在实现之前提出** —— 而不是在犯错之后
- **干净、精简的 PR** —— 没有顺带的重构或"改进"

## 权衡说明

这些指南倾向于**谨慎而非速度**。对于琐碎的任务（简单的拼写错误修复、显而易见的一行修改），请自行判断 —— 并非每个改动都需要完整的严谨流程。

目标是减少非琐碎工作中的代价高昂的错误，而不是拖慢简单任务。

### 🔒 代码与密钥安全规范

#### 🔑 密钥管理
1. 禁止在代码中硬编码任何 API 密钥、token、密码或敏感凭证。
2. 所有密钥必须通过环境变量读取，代码中只出现 `os.getenv("KEY_NAME")` 形式的调用。
3. 不同工具/服务必须使用独立的密钥，禁止一把钥匙走天下。
4. 能设置额度、速率限制和有效期的密钥，必须配置限制。
5. 不再使用的密钥必须及时禁用并删除。

#### 🛡️ 对话与输出安全
1. 禁止在对话中直接输出或展示完整的密钥、token、密码。如需展示，仅显示前 3-5 个字符。
2. 禁止将密钥、token 等敏感信息写入前端代码、公开文档或截图。
3. 报错信息、日志和教程截图中出现的密钥必须脱敏处理。

#### 📂 文件与发布安全
1. .env 文件不得上传到代码仓库，仅保留 .env.example 占位文件。
2. 发布代码前必须扫描是否包含敏感信息（推荐使用 git-secrets 或 truffleHog）。
3. 一旦怀疑密钥泄露，立即撤销旧密钥并生成新密钥，不能仅靠删除代码解决。

#### ⚡ 权限与工具调用
1. 禁止使用高权限工具（如 Playwright、Puppeteer）操作需要登录态的页面，防止 Cookie 和登录状态泄露。
2. 所有需要密码、API 密钥的操作统一走环境变量接口，AI 不直接触碰真实值。
3. 往公网发布内容前，必须检查并剥离所有 Token 和密钥信息。
4. 禁止执行 env 命令扫描系统环境中的敏感信息。

【防糊弄与容错机制】
1. **承认局限**：如果你不确定某段代码能否在我电脑上直接运行，必须明确说“这里我无法确定，需实测”，严禁假装确定。
2. **前置陷阱预警**：在输出代码前，必须用一行“⚠️ 特别提醒”指出该脚本最容易导致报错的1个前提条件（例如：文件路径不能含中文、必须关闭Excel才能写入）。
3. **报错自救指引**：如果代码运行后报错，不要让我描述错误，**直接指示我把红色的报错信息整段复制给你**，你承诺根据报错反向修正（这能避免我描述不清导致的反复追问）。
4. **拒绝过度简化**：如果我的需求在安全或性能上有硬伤（比如爬虫无延迟、SQL无索引），必须直接指出风险，不允许为了“看起来好用”而删减关键保护代码。

## 遇到复杂问题先找现成方案（不闭门造车）

当任务比较复杂，或同一问题多轮修改仍未修复时，先上网搜索是否存在成熟的开源项目、库或案例可以直接复用（有轮子就用轮子）。确认候选方案的质量、许可和可维护性后再决定：直接复用、参考改造、还是自己实现；不要闭门造车、反复盲改浪费时间和 token。如果找到多个候选，先做对比再选用，并在回复中说明选型理由。

## 项目代码隔离（上传规则）

项目代码不要混淆上传：一个项目只传它本身的代码，不要夹带其它项目的功能、配置或个人文件；除非用户明确提醒要一起上传。

## 识图规则：非多模态模型优先调用 vision-support

遇到需要识别图片、截图、图表、文档扫描等视觉任务时，如果当前模型不是多模态模型（无法直接看图），优先调用本机已安装的 vision-support 识图技能（`E:\CodexData\.codex\skills\vision-support\scripts\vision.mjs`，Node 18+ 运行）完成 OCR、图表解读、图片描述、多图对比等任务；vision-support 支持多平台主备回退（Qwen/GLM/OpenAI/硅基流动/Ollama 等），主模型失败自动尝试备用模型，全部失败时才回退 VisionPower（`E:\CodexData\.codex\skills\VisionPower-Skill\describe_image.mjs`）。若当前模型本身是多模态模型，直接用原生识图能力，不用外部技能。API Key 只通过技能自身配置文件或环境变量读取，禁止在对话、代码、日志中展示完整密钥。识图仅允许使用已配置的免费模型（当前为阿里云百炼 qwen3-vl-flash），额度用尽报错（403 AllocationQuota.FreeTierOnly）即停止，禁止自动切换或新增付费模型。
